# Mobile and stylus drawing input and client-side stroke rendering (finger, Apple Pencil on iPad Safari, S Pen on Chrome / Samsung Internet), as of October 2026

Scope note: "Not The Louvre" (SvelteKit / Svelte 5 on Cloudflare Workers). The canonical artwork is a vector stroke document (`{version, kind, width, height, background, strokes:[{color, size 1..64, points:[[x,y],...]}]}`) with integer points, no pressure and no timing. The server re-renders it as SVG and rasterizes it with `@resvg/resvg-wasm`. Repo facts below come from reading branch `audit/fix-everything` (commit 9d09a29) and are cited by repo path.

Browser support data was read from the MDN browser-compat-data JSON on GitHub (main branch, pulled 2026-10-23). "Samsung Internet" and "Android WebView" are recorded there as `mirror` of Chrome Android, meaning they inherit Chrome's version data. I did not verify any Safari 27 / iPadOS 27 changes, if those shipped in September 2026. The newest WebKit release posts I saw were for Safari 26.5 (May 2026).

## 1. Pointer Events capability today on iPadOS/iOS Safari, Android Chrome and Samsung Internet (pressure, tilt, angles, coalesced/predicted events, pointerrawupdate, Pencil hover/squeeze/double-tap, S Pen, finger pressure and velocity-simulated pressure)

### Takeaway
Since Safari 18.2 (December 2024), all three target browsers support the full Pointer Events toolkit a drawing app needs: `pressure`, `tiltX/Y`, `altitudeAngle/azimuthAngle`, `getCoalescedEvents()` and `getPredictedEvents()`. Safari still lacks `pointerrawupdate`. Apple Pencil squeeze and double-tap have no web API. Finger "pressure" is unusable. On iOS it comes through as 0, on Android as raw, device-dependent contact pressure. Good apps therefore trust pressure only from `pointerType === 'pen'` and simulate it from velocity for fingers and mice. The project today uses none of this: no coalesced events, no pressure, integer points.

### Cited Findings

**Support matrix (MDN BCD, Oct 2026)**
- `PointerEvent.getCoalescedEvents`: Chrome 58, Safari 18.2 (iOS mirrors desktop), Firefox 59, Samsung Internet and WebView mirror Chrome Android. — [MDN BCD api/PointerEvent.json](https://github.com/mdn/browser-compat-data/blob/main/api/PointerEvent.json)
- `PointerEvent.getPredictedEvents`: Chrome 77, Safari 18.2, Firefox 89. — [MDN BCD api/PointerEvent.json](https://github.com/mdn/browser-compat-data/blob/main/api/PointerEvent.json); caniuse shows Safari and iOS Safari unsupported through 18.1 and supported from 18.2 to 26.3 — [caniuse getPredictedEvents](https://caniuse.com/mdn-api_pointerevent_getpredictedevents)
- `altitudeAngle` / `azimuthAngle`: Chrome 86, Safari 18.2, Firefox 131. `pressure`, `tiltX/Y`, `twist`, `tangentialPressure`: Safari 13+, Chrome 55/57+. `persistentDeviceId`: Chrome 128 only, not Safari. — [MDN BCD api/PointerEvent.json](https://github.com/mdn/browser-compat-data/blob/main/api/PointerEvent.json)
- `pointerrawupdate`: Chrome 77, Firefox 148, **not supported in Safari**. Before Chrome 142 it was exposed to non-secure contexts; it now requires a secure context. — [MDN BCD api/Element.json](https://github.com/mdn/browser-compat-data/blob/main/api/Element.json); the spec marks `onpointerrawupdate` `[SecureContext]` and says predicted events for `pointerrawupdate` "will, for performance reasons, usually be an empty list" — [W3C Pointer Events (editor's draft)](https://w3c.github.io/pointerevents/)
- WebKit's own Safari 18.2 notes: `getPredictedEvents()` returns "estimated future pointer positions" based "on past points, current velocity, and trajectory"; `getCoalescedEvents()` returns events "that were coalesced (merged) into a single pointermove"; `altitudeAngle/azimuthAngle` let you "determine the angle between Apple Pencil and the X-Y or Y-Z planes of the screen". The same release also fixed pointer capture events to be trusted and composed. — [WebKit Features in Safari 18.2](https://webkit.org/blog/16301/webkit-features-in-safari-18-2/)
- Older MDN mirrors still list `getCoalescedEvents` as "No support" in Safari. They predate 18.2 and are stale. — [WebSearch summary of mirror pages, e.g. getdocs.org](https://getdocs.org/Web/API/PointerEvent/getCoalescedEvents)

**Why coalesced events matter (frame-aligned input)**
- Since Chrome 60, Chrome holds back continuous events (`pointermove`, `touchmove`, etc.) and delivers them just before `requestAnimationFrame` callbacks. That is roughly one per frame. `getCoalescedEvents()` (Chrome 58) is how an app recovers the full path. (The post is from 2017 but still describes the model.) — [Chrome for Developers: Aligned input events](https://developer.chrome.com/blog/aligning-input-events)
- WebKit iOS builds the coalesced and predicted lists from UIKit's `coalescedTouchesForTouch:` / `predictedTouchesForTouch:`, so Pencil's high-rate samples come through `getCoalescedEvents()`. — [WebKit source: WKTouchEventsGestureRecognizer.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/ios/WKTouchEventsGestureRecognizer.mm); [WebKit source: NativeWebTouchEventIOS.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/Shared/ios/NativeWebTouchEventIOS.mm)
- Developer report from March 2025, unanswered: with Apple Pencil Pro on iPad Safari, plain `onPointerMove` produced "visibly segmented, straight-line strokes" while `onTouchMove` drew smooth curves. The poster suspected a lower PointerEvent sampling rate. — [Apple Developer Forums thread 776468](https://developer.apple.com/forums/thread/776468)
- tldraw dispatches coalesced events for high-fidelity tools but deliberately **skips them on iOS**: `!tlenv.isIos && currentTool.useCoalescedEvents && e.getCoalescedEvents ? e.getCoalescedEvents() : [e]`. The code comment says the API is sometimes missing on iOS in non-https local mode, and that "the intent here is to have `useCoalescedEvents` disabled for iOS". — [tldraw useCanvasEvents.ts](https://github.com/tldraw/tldraw/blob/main/packages/editor/src/lib/hooks/useCanvasEvents.ts)

**Pressure / tilt semantics per engine**
- Spec: for hardware without pressure support, `pressure` "MUST be 0.5 when in the active buttons state and 0 otherwise". `altitudeAngle` defaults to π/2 and `azimuthAngle` to 0 when the hardware has no tilt. Hovering pens report `buttons = 0`, and events stop when the pen leaves the digitizer's hover range. — [W3C Pointer Events](https://w3c.github.io/pointerevents/)
- **WebKit iOS (source):** `touchPoint.force = touch.maximumPossibleForce > 0 ? touch.force / touch.maximumPossibleForce : 0`, and `PointerEvent.pressure` is set from that force for both touch and stylus. `pointerType` is `pen` only when `UITouchTypeStylus`. `altitudeAngle` is read only for stylus (touch gets π/2). `tiltX/Y` are derived from altitude/azimuth. — [WebKit WKTouchEventsGestureRecognizer.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/ios/WKTouchEventsGestureRecognizer.mm); [WebKit PointerEventIOS.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/dom/ios/PointerEventIOS.cpp)
- **WebKit iOS twist / barrel roll:** the Pencil Pro roll angle reaches `twist` only behind `_shouldExposeRollAngleAsTwist`, an experimental flag (WebKit bug 298276 "[Experimental] Expose roll angle of Apple Pencil for twist"). In April 2026 a reporter said `twist` "always seems to be 0" on iPadOS 26.4.1 with an M4 iPad Pro and Pencil Pro. — [WebKit WKTouchEventsGestureRecognizer.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/ios/WKTouchEventsGestureRecognizer.mm); [WebKit bug 296943](https://bugs.webkit.org/show_bug.cgi?id=296943)
- **Chromium (Android, source):** `webPointerProperties.force = pressure`, the raw Android `MotionEvent` pressure. Tilt and twist are set only for `ToolType::STYLUS` and zeroed for fingers. Blink's `GetPointerEventPressure` returns 0 when no buttons are pressed, 0.5 **only if the force is NaN**, and otherwise the raw value. `altitudeAngle/azimuthAngle` are computed from tilt, and `tiltX/Y` are rounded to integers. — [Chromium blink_event_util.cc](https://github.com/chromium/chromium/blob/main/ui/events/blink/blink_event_util.cc); [Chromium pointer_event_factory.cc](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/events/pointer_event_factory.cc); [Chromium motion_event_android.cc](https://github.com/chromium/chromium/blob/main/ui/events/android/motion_event_android.cc)
- Android `getPressure()` can exceed 1 on some devices (SDL clamps it). — [SDL commit](https://hg.libsdl.org/SDL/rev/9b60f0a1cae8)

**Apple Pencil hover, squeeze, double-tap**
- Safari 16.1 (October 2022) added Apple Pencil hover on the M2 iPad Pro, which detects the Pencil up to 12 mm above the screen. Sites can respond with hover states. — [MacRumors, 2022-10-24](https://www.macrumors.com/2022/10/24/apple-safari-16-1-launch/)
- WebKit engineer (2025): "we already dispatch hover events for Apple Pencil hover". A later comment says hovering `pointermove` "does not show tilt or roll". — [WebKit bug 296943](https://bugs.webkit.org/show_bug.cgi?id=296943)
- Asked on the Apple forums in July 2024 whether Mobile Safari exposes Pencil Pro hover or squeeze events: no answer from Apple. — [Apple Developer Forums thread 760238](https://developer.apple.com/forums/thread/760238)

**S Pen (Galaxy) on the web**
- On Chromium Android the stylus arrives as `pointerType: 'pen'` (the `ToolType` STYLUS→pen mapping). Pressure is raw `MotionEvent` pressure and tilt comes from Android orientation/tilt. — [Chromium blink_event_util.cc](https://github.com/chromium/chromium/blob/main/ui/events/blink/blink_event_util.cc); [Chromium motion_event_android.cc](https://github.com/chromium/chromium/blob/main/ui/events/android/motion_event_android.cc)

- Samsung developer forum: the S Pen side button "is exposed through the S Pen Remote SDK for native Android apps" and "JavaScript support / Browser event is not available". A Galaxy Tab S9 FE+ developer got all pointer events but no event for the side-button press. — [Samsung Developer Forum 7914](https://forum.developer.samsung.com/t/how-to-handle-samsung-s-pen-button-event-in-the-browser-javascript/7914); [Samsung Developer Forum 38112](https://forum.developer.samsung.com/t/galaxy-tab-s9-fe-cant-get-any-spen-specific-events/38112)
- S Pen hover (Air View) triggers mouseover/hover in Samsung Internet, per community reports. — [Samsung Community thread](https://us.community.samsung.com/t5/Galaxy-S22/S-Pen-mouseover-events-in-web-browsers/td-p/2201606)
- The S Pen hardware advertises 4096 pressure levels. — [PhoneArena](https://www.phonearena.com/news/s-pen-how-to-new-features_id118330)

**How polished apps decide "real pressure" and simulate it for fingers**
- tldraw: `isPenOrStylus = (isPen && z !== 0) || (z > 0 && z < 0.5) || (z > 0.5 && z < 1)`. A pen whose first point reports z = 0 is treated as a "broken pen" and handled like a mouse. Real pressure is stored as `+(z * 1.25).toFixed(2)`. Non-pressure input stores a constant 0.5 and drops the z dimension entirely (2D points). Shapes record `isPen`. — [tldraw Drawing.ts](https://github.com/tldraw/tldraw/blob/main/packages/tldraw/src/lib/shapes/draw/toolStates/Drawing.ts); the tldraw docs say real pressure means "a pen pointer with non-zero pressure, or any pointer whose pressure isn't a constant 0, 0.5, or 1", and mouse and finger strokes "use simulated pressure instead" — [tldraw Pen mode docs (created 2026-01-31)](https://github.com/tldraw/tldraw/blob/main/apps/docs/content/sdk-features/pen-mode.mdx)
- Excalidraw: `const simulatePressure = event.pressure === 0.5`. It persists per-point `pressures` only when not simulating. — [Excalidraw App.tsx](https://github.com/excalidraw/excalidraw/blob/master/packages/excalidraw/components/App.tsx)
- perfect-freehand velocity model (v1.2.3): `sp = min(1, distance / size)`, `rp = min(1, 1 - sp)`, `pressure = min(1, prev + (rp - prev) * (sp * 0.275))`. Faster movement (bigger distance between samples) gives a lower pressure and a thinner line. The initial pressure is averaged over the first few points "to prevent fat starts". — [perfect-freehand simulatePressure.ts](https://github.com/steveruizok/perfect-freehand/blob/main/packages/perfect-freehand/src/simulatePressure.ts); [constants.ts](https://github.com/steveruizok/perfect-freehand/blob/main/packages/perfect-freehand/src/constants.ts); [getStrokeOutlinePoints.ts](https://github.com/steveruizok/perfect-freehand/blob/main/packages/perfect-freehand/src/getStrokeOutlinePoints.ts)

**What the project does today**
- Uses Pointer Events with `setPointerCapture`, an `isPrimary` filter and an `activePointerId` guard. A window-level `pointerup` / `pointercancel` / `blur` safety net is shared by the studio canvas and the avatar pad. — [repo: apps/web/src/lib/features/studio-drawing/pointer-drawing.ts](apps/web/src/lib/features/studio-drawing/pointer-drawing.ts); [repo: components/DrawingCanvas.svelte](apps/web/src/lib/features/studio-drawing/components/DrawingCanvas.svelte); [repo: home-entry-scene/components/AvatarSketchpad.svelte](apps/web/src/lib/features/home-entry-scene/components/AvatarSketchpad.svelte)
- Reads only `clientX/clientY`: no `getCoalescedEvents`, `getPredictedEvents`, `pressure`, tilt or `timeStamp`. Points are clamped and `Math.round`ed to integers in 768×768 document space. Consecutive duplicate points are dropped. — [repo: stroke-json/document.ts `clampDrawingPoint`](apps/web/src/lib/features/stroke-json/document.ts); [repo: stroke-json/responsive-editing.ts](apps/web/src/lib/features/stroke-json/responsive-editing.ts)
- `hasLostPrimaryButton` is narrowed to mice because "a stylus can momentarily report `buttons: 0` mid-stroke". This is a pen-aware decision that already exists. — [repo: pointer-drawing.ts](apps/web/src/lib/features/studio-drawing/pointer-drawing.ts)
- No eraser and no undo exist in the studio or avatar code on this branch. A grep for "undo|eraser" across tracked source finds only docs/specs and `home-entry-scene/canvas/museum-canvas.ts`. — [repo grep, branch audit/fix-everything](apps/web/src/lib/features/studio-drawing/state/drawing.svelte.ts)

### Inferences
- On iOS, finger `pressure` is effectively 0 on every iPad and every iPhone without 3D Touch, because `maximumPossibleForce` is 0. That deviates from the spec's 0.5. On Android, finger `pressure` is a noisy contact-area pseudo-pressure. Pressure must therefore be gated on `pointerType === 'pen'` (plus tldraw's "not a constant 0/0.5/1" check). Excalidraw's `pressure === 0.5` test would misclassify iOS finger input (pressure 0) as real pressure. Avoid that pattern.
- Plain `pointermove` gives roughly 60–120 samples/s, while a Pencil reports at a higher rate. Iterating `getCoalescedEvents()` is the single biggest fidelity win and works in all three target browsers. tldraw's iOS opt-out is a reason to test on hardware, not a reason to skip it. Feature-detect (`'getCoalescedEvents' in PointerEvent.prototype`) and fall back to `[e]`.
- perfect-freehand's simulated pressure depends on distance per sample, not time. Switching to coalesced events (denser samples) makes simulated strokes thicker, and 60 Hz vs 120 Hz devices will feel different. Two ways to keep it consistent across devices: compute simulated pressure from velocity in px/ms using `event.timeStamp`, or resample the input to a fixed spatial step before feeding perfect-freehand.
- Hover (Pencil on M2+ iPads, S Pen Air View) arrives as `pointermove` with `pointerType: 'pen'` and `buttons === 0`. Use it for a brush-size/colour preview cursor (the app already has an overlay preview canvas). Do not draw on it.
- Squeeze, double-tap and the S Pen side button cannot be relied on from the web. UI must not depend on them.

### Gaps
- No hands-on device verification of what iPadOS 26 Safari reports for finger `pressure`. The value 0 is inferred from WebKit source. Pencil hover tilt is also unverified beyond the bug comment.
- No authoritative Samsung documentation for S Pen in Samsung Internet. Whether the side button maps to `buttons & 2` in Chrome or Samsung Internet on current One UI is unresolved (Chromium maps it, Samsung forum users report no event).
- Whether Chrome Android actually produces non-empty `getPredictedEvents()` (input prediction enabled by default) could not be confirmed from a primary source. The spec allows "zero or more".
- Not verified: whether tldraw's iOS opt-out of coalesced events is still justified on Safari 18.2+.

## 2. Lowest-latency rendering: desynchronized canvas, OffscreenCanvas in a worker, WebGL/WebGPU, incremental in-progress stroke vs re-render. What actually helps on iOS Safari and Android Chrome in 2025–2026

### Takeaway
I found no credible 2025–2026 measurements of web ink latency on iPad Safari or Android Chrome. What exists is mechanism-level guidance and estimates.

For a 768×768 canvas, the practical gains come from four things: keep the main thread free, paint once per `requestAnimationFrame` from the coalesced samples, split a "dry" committed bitmap from a "wet" in-progress layer, and draw a short predicted tail. `desynchronized: true` is a progressive enhancement with real caveats. OffscreenCanvas workers, WebGL/WebGPU and the Ink API add complexity without a demonstrated win for this workload on iOS.

The project currently paints synchronously on every `pointermove`. In "small document" mode it deep-clones the whole document per point. Its backing store is not DPR-aware.

### Cited Findings
- `desynchronized` "bypasses the DOM update path", lets the system skip compositing and sometimes sends the buffer straight to the display controller. Tearing is possible on front-buffer devices such as ChromeOS. A translucent canvas can use it only if no other DOM elements sit above it. Feature-detect via `getContextAttributes().desynchronized`. Latency over 50 ms is cited as harmful to hand-eye coordination. The article contains no measured latency reductions. **The article was last updated 2019-05-02 and is old.** — [Chrome for Developers: Low-latency rendering with the desynchronized hint](https://developer.chrome.com/blog/desynchronized)
- BCD: the 2D `desynchronized` option is listed for Chrome Android 75, desktop Chrome 81 (ChromeOS and Windows only) and **Safari 15**. Not in Firefox. — [MDN BCD api/HTMLCanvasElement.json](https://github.com/mdn/browser-compat-data/blob/main/api/HTMLCanvasElement.json). No source says Safari actually shortens its rendering path when the option is set. WebKit engineers reportedly said nothing "overly complicated" is done for low latency in the iOS web stack (second-hand, Chromium thread) — [Chromium graphics-dev: Delegated Ink Trails](https://groups.google.com/a/chromium.org/g/graphics-dev/c/cErEIr4NECg/m/qgidUJHvAwAJ)
- Anecdote: one GitHub project skipped the desynchronized hint on mobile because it rendered as a black canvas on some Android browsers. — [GitHub PR: skip desynchronized canvas hint on mobile](https://github.com/thanujsilla/pair_programming/pull/6)
- Microsoft's ink explainer: OS compositors "typically introduce a frame of latency". Desynchronized canvas relies on hardware overlays that cannot alpha-blend with content beneath and need an orientation-matched buffer. It "is inherently unable to synchronize with other HTML content", so wet-to-dry ink handoff can show one frame with no ink or with both. The sample code's comment estimates that `pointerrawupdate` plus JS prediction "can reduce latency by 16+ ms". — [MSEdgeExplainers WebInkEnhancement](https://github.com/MicrosoftEdge/MSEdgeExplainers/blob/main/WebInkEnhancement/explainer.md)
- Ink API (`navigator.ink.requestPresenter`, delegated ink trails): Chrome 94 only, experimental, not in Safari or Firefox. — [MDN BCD api/Ink.json](https://github.com/mdn/browser-compat-data/blob/main/api/Ink.json). Chromium's implementation path is a Windows DirectComposition swap chain — [Chromium delegated_ink_point_renderer_gpu.h](https://chromium.googlesource.com/chromium/src/+/d4afc97b7/ui/gl/delegated_ink_point_renderer_gpu.h). `expectedImprovement` was removed in 2024 for lack of usage — [blink-dev intent](https://groups.google.com/a/chromium.org/g/blink-dev/c/Gtbh2fkpdxI/m/VLV2UFUvAAAJ)
- OffscreenCanvas and `transferControlToOffscreen`: Chrome 69, Safari 16.4, Firefox 105. — [MDN BCD api/OffscreenCanvas.json](https://github.com/mdn/browser-compat-data/blob/main/api/OffscreenCanvas.json). The Microsoft explainer says the benefit is separating pointer handling "from other main thread logic" — [MSEdgeExplainers WebInkEnhancement](https://github.com/MicrosoftEdge/MSEdgeExplainers/blob/main/WebInkEnhancement/explainer.md)
- WebGPU canvas context: Chrome Android 121, Safari 26, Firefox 141 (Windows only). WebGL2: Safari 15. — [MDN BCD api/HTMLCanvasElement.json](https://github.com/mdn/browser-compat-data/blob/main/api/HTMLCanvasElement.json); Safari 26.0 shipped WebGPU — [WebKit Features in Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)
- Native baseline for comparison: Apple said iPadOS 13 cut Pencil latency from 20 ms to 9 ms, and PencilKit gives native apps that engine. This is native-only, not web. — [9to5Mac, 2019](https://9to5mac.com/2019/06/06/pencilkit-apple-wwdc/). A review site claims photodiode measurements (~22 ms iPad Pro M2, 41–69 ms Android styluses) with an unclear method and conflicting numbers; **not reliable** — [lifetips.alibaba.com](https://lifetips.alibaba.com/tech-efficiency/apple-pencil-review)
- The spec says predicted events are valid "until the next pointer event is dispatched", so they must be drawn as a throwaway tail. The Microsoft explainer warns that inaccurate prediction "may lead to artifacts". — [W3C Pointer Events](https://w3c.github.io/pointerevents/); [MSEdgeExplainers](https://github.com/MicrosoftEdge/MSEdgeExplainers/blob/main/WebInkEnhancement/explainer.md)
- The tldraw performance docs recommend zoom-aware stroke widths and `editor.getEfficientZoomLevel()` on large documents to avoid jank during camera moves. — [tldraw performance docs](https://tldraw.dev/sdk-features/performance)

**What the project does today**
- Paints **synchronously inside each `pointermove`**, not batched per frame. Each paint fills the background, `drawImage`s the committed-stroke cache and **re-strokes the entire active stroke** (`renderDrawingStroke` walks all points). — [repo: DrawingCanvas.svelte `renderCurrentDocument`](apps/web/src/lib/features/studio-drawing/components/DrawingCanvas.svelte); [repo: stroke-json/canvas.ts](apps/web/src/lib/features/stroke-json/canvas.ts)
- Below 64 strokes and 1,200 points ("non-responsive" mode), each new point runs `cloneDrawingDocumentV2(drawingDocument)`, pushes the point, commits the new document (which triggers Svelte reactivity) and re-renders the whole document without the cache. That is O(document) work per pointer sample. Above the threshold it switches to the buffered `activeStroke` + committed cache path. — [repo: DrawingCanvas.svelte `appendPoint`](apps/web/src/lib/features/studio-drawing/components/DrawingCanvas.svelte); [repo: stroke-json/responsive-editing.ts `RESPONSIVE_DRAWING_THRESHOLDS`](apps/web/src/lib/features/stroke-json/responsive-editing.ts)
- `activeStroke` is a Svelte `$state` (deeply proxied), so every `points.push` goes through the proxy. — [repo: DrawingCanvas.svelte](apps/web/src/lib/features/studio-drawing/components/DrawingCanvas.svelte)
- The canvas backing store is a fixed `width={768} height={768}`, CSS-stretched with `h-full w-full`. There is no `devicePixelRatio` handling. `getContext('2d')` is called with no options. — [repo: DrawingCanvas.svelte](apps/web/src/lib/features/studio-drawing/components/DrawingCanvas.svelte)
- A second absolutely positioned overlay canvas, the brush preview, sits above the drawing canvas and is cleared and redrawn on every `pointermove`, including during strokes and for touch. — [repo: DrawingCanvas.svelte `drawPreviewOnOverlayAt`](apps/web/src/lib/features/studio-drawing/components/DrawingCanvas.svelte)
- `getCanvasDrawingPoint` calls `getBoundingClientRect()` on every move event. — [repo: pointer-drawing.ts](apps/web/src/lib/features/studio-drawing/pointer-drawing.ts)

### Inferences
- **Recommended pipeline, in priority order:**
  1. In `pointermove`, push the coalesced samples (float x/y in document space, pressure, `timeStamp`) into a plain, non-reactive array. Do not use `$state` here, and do not clone the document per sample.
  2. Schedule a single `requestAnimationFrame` paint.
  3. Paint the dry layer as one cached bitmap (`drawImage`) and the wet layer as only the active stroke. For constant-width round-cap polylines with opaque colours, append only the new segments and never clear. For variable width (perfect-freehand), re-tessellate just the active stroke each frame, as tldraw and Excalidraw do.
  4. Draw `getPredictedEvents()` points as a tail on a separate overlay that is cleared each frame.
  5. Commit to the reactive document once, on `pointerup`.

  This removes the O(n²)-per-stroke behaviour of non-responsive mode, which is exactly the small-document case most party-game drawings fall into.
- Make the backing store DPR-aware: `canvas.width = cssWidth * devicePixelRatio`, then `ctx.setTransform(scale, 0, 0, scale, 0, 0)` with scale = backing px / 768, and keep the document coordinates at 768. Today an iPad at 2× DPR showing the canvas at ~800–1000 CSS px upscales the 768-px bitmap about 2–2.6×, so strokes look soft. Cap the backing store (e.g. 2048²) for memory.
- Treat `desynchronized: true` as opt-in on Chrome Android / ChromeOS only, verified via `getContextAttributes()`. It requires that nothing composites above the canvas, so the brush-preview overlay would have to move into the same canvas or go away. Given the black-canvas anecdotes and the lack of a Safari benefit, do not make it the default without a device test matrix.
- OffscreenCanvas in a worker does not cut input latency here: input still lands on the main thread and must be `postMessage`d. It only helps if main-thread jank (Svelte effects, network, GC) is measured as the problem. WebGL/WebGPU is unnecessary at 768² with opaque round strokes, because Canvas2D is GPU-backed in both engines. Reserve it for brush textures or a gallery-wide WebGL scene.
- Cache the canvas `DOMRect` on `pointerdown` and on resize or scroll instead of reading it per event.

### Gaps
- No controlled latency measurements (camera or photodiode) for web canvas on iPad Safari or Android Chrome in 2024–2026. Any latency claims should come from the team's own tests, e.g. a high-speed phone camera at 240 fps filming a Pencil stroke on a test page.
- No primary source confirms whether Safari's `desynchronized` (listed in BCD since 15) changes the presentation path.
- Delegated ink trails: no confirmation of any Android shipping. Treat as Windows-only and experimental.

## 3. Palm rejection and gestures on the web: touch-action, pen-mode filtering by pointerType, two-finger pan/pinch-zoom, two-finger-tap undo, suppressing iOS Scribble / selection / magnifier / double-tap zoom / edge-swipe-back, Android back gesture

### Takeaway
The industry pattern (tldraw, Excalidraw) is an automatic **pen mode**: the first direct-display `pen` pointerdown switches the canvas to ignore `touch` pointers, a visible "exit pen mode" control turns it off, and fingers then handle pan, pinch and undo taps. On iPad Safari, cancelling pointer events is **not** enough to stop the magnifier, callout and Scribble. You must `preventDefault()` a **non-passive `touchstart`** on the canvas and add `user-select: none` / `-webkit-touch-callout: none`. Svelte 5 makes `ontouchstart` passive by default, so this must be wired with `on()` from `svelte/events`. Edge-swipe-back can be blocked only in Safari in-browser, via an edge-zone `touchstart` `preventDefault`. The project today has `touch-action: none` and nothing else: no pen mode, no gestures, no touchstart cancel.

### Cited Findings
- **tldraw pen mode:** "When a stylus touches a touch-capable screen ... the editor turns on pen mode and ignores other pointer input". It only turns on for direct-display pens, not desktop tablets. While on, "the editor drops pointer down, move, and up events from any non-pen input". The toolbar UI still works with fingers. An "Exit pen mode" helper button is shown because "there's no way to turn pen mode off with a finger on the canvas itself". Hardware eraser (button 5) switches to the eraser tool temporarily. — [tldraw Pen mode docs (2026-01-31)](https://github.com/tldraw/tldraw/blob/main/apps/docs/content/sdk-features/pen-mode.mdx)
- tldraw implementation: `isDirectDisplayPen(e)` returns `e.pointerType === 'pen' && tlenv.isTouchDevice`. In pen mode, `pointercancel` from non-pen pointers is ignored ("a cancelled touch is usually a rejected palm"). `touchstart` and `touchend` on the canvas are `preventDefault`ed. — [tldraw useCanvasEvents.ts](https://github.com/tldraw/tldraw/blob/main/packages/editor/src/lib/hooks/useCanvasEvents.ts); [tldraw utils/pointer.ts](https://github.com/tldraw/tldraw/blob/main/packages/editor/src/lib/utils/pointer.ts)

- Scribble is on by default when a Pencil is paired and can be turned off only in Settings > Apple Pencil. — [Apple Support: Scribble](https://support.apple.com/guide/ipad/enter-text-with-scribble-ipad355ab2a7/ipados). To prevent defaults, use `on` from `svelte/events` (e.g. inside an action) rather than `addEventListener`. — [Svelte docs: Basic markup / events](https://svelte.dev/docs/svelte/basic-markup)

**What the project does today**
- The drawing canvas has inline `touch-action: none`, and the avatar pad CSS has `touch-action: none`. `draggable="false"` plus a `dragstart` `preventDefault`. Global CSS sets `touch-action: manipulation` on buttons and links. The viewport meta is `width=device-width, initial-scale=1`. — [repo: DrawingCanvas.svelte](apps/web/src/lib/features/studio-drawing/components/DrawingCanvas.svelte); [repo: AvatarSketchpad.svelte (line ~1044)](apps/web/src/lib/features/home-entry-scene/components/AvatarSketchpad.svelte); [repo: apps/web/src/routes/layout.css (~line 237)](apps/web/src/routes/layout.css); [repo: apps/web/src/app.html](apps/web/src/app.html)
- There is no `pointerType` filtering and no pen mode. The `isPrimary` check does not reject palms: the spec designates a primary pointer *per pointer type*, so a palm touch landing before the pen is itself primary and starts a stroke. There is no `touchstart` cancel, no `-webkit-touch-callout` or `user-select` on the canvas, no pinch/pan/zoom and no gesture undo. — [repo: DrawingCanvas.svelte `startDrawing`](apps/web/src/lib/features/studio-drawing/components/DrawingCanvas.svelte); [W3C Pointer Events (primary pointer per type)](https://w3c.github.io/pointerevents/)

### Inferences
- **Recommended input state machine:**
  - **Pen mode.** On the first `pointerdown` with `pointerType === 'pen'` on a touch device, set `penMode = true` for the session and keep a visible toggle. In pen mode, `touch` pointers never draw. One finger pans (when zoom > 1), two fingers pinch or pan, and two- and three-finger taps run undo and redo.
  - **No pen detected (phones).** One finger draws. If a second touch lands within ~150–250 ms or ~10–20 px of the stroke start, discard the in-progress stroke and switch to pinch/pan. Fingers almost always land a few ms apart. A two-finger tap (both up within ~250 ms, movement < ~10 px) is undo, a three-finger tap is redo, and a quick pinch is fit-to-screen.
  - **`pointercancel`.** For the active pen pointer, commit or discard deliberately. For touch pointers in pen mode, ignore it (rejected palm).
- **iOS hardening for the canvas element:**
  - A non-passive `touchstart` `preventDefault` attached with `on(canvas, 'touchstart', fn, { passive: false })` from `svelte/events`.
  - CSS: `user-select: none; -webkit-user-select: none; -webkit-touch-callout: none; -webkit-tap-highlight-color: transparent; touch-action: none`.
  - `gesturestart` / `gesturechange` `preventDefault` on the stage, so Safari never page-zooms during an in-app pinch.
  - Clear `document.getSelection()` on pointerdown.
  - An edge-zone `touchstart` `preventDefault` only while drawing, and only in Safari tabs. It will not work as a standalone home-screen app.
- **Android system back gesture:** I found no web mechanism to block it. Mitigate by keeping the drawable area inset from the screen edges on phones and by guarding unsaved work, e.g. a history entry plus `popstate`/Navigation API (Safari 26.2 added the Navigation API, [WebKit Safari 26.2](https://webkit.org/blog/17640/webkit-features-for-safari-26-2/)) or local draft persistence. The app already has draft sessions in `stroke-json/drafts.ts`.
- tldraw's own code is under the proprietary "tldraw license" (a production deployment needs a license), while perfect-freehand and Excalidraw are MIT. Copy patterns, not tldraw code. — [tldraw LICENSE.md](https://github.com/tldraw/tldraw/blob/main/LICENSE.md); [Excalidraw repo (MIT)](https://github.com/excalidraw/excalidraw)

### Gaps
- Not verified on hardware: whether iPadOS 26's system palm rejection delivers palm touches to Safari as `pointercancel`, or suppresses them entirely while the Pencil is down.
- No primary source on blocking the Android 10+ system back gesture from a web page. The statement that it cannot be blocked is an inference.
- Whether Scribble can still hijack strokes after the `touchstart` cancel, with Scribble left on, is not established by any source. Test both settings.

## 4. Stroke smoothing and pressure-to-width: perfect-freehand (maintenance, license, quality) and alternatives; how tldraw, Excalidraw, FigJam etc. implement streamlining, thinning, tapering and predicted points

### Takeaway
perfect-freehand is still the de facto web library for pressure-sensitive outlines. It is MIT, small, stable, at v1.2.3 (Feb 2026, a tooling modernization) and in maintenance mode, with a Rust port. tldraw ships a vendored fork, and Excalidraw uses it for variable-width freedraw while adding a separate constant-width outline engine. Both tune `thinning`, `streamline`, `smoothing` and easing per input type: real pen pressure vs simulated pressure for finger and mouse. The project's current round-cap polylines have no smoothing at all, and integer quantization makes thin strokes jaggy.

### Cited Findings
- perfect-freehand: MIT, ~5.8k stars, 22 open issues, not archived, last push 2026-04-13. npm `1.2.3` published 2026-02-01, previous release `1.2.2` in March 2024. The February 2026 commits are "Modernize build tooling and dev infrastructure for 2026 (#96)" and a README link to a new Rust port. Unpacked size about 112 kB (the runtime is a few kB). — [GitHub steveruizok/perfect-freehand](https://github.com/steveruizok/perfect-freehand); [npm perfect-freehand](https://www.npmjs.com/package/perfect-freehand)
- API and options (defaults): `size` 8, `thinning` 0.5, `smoothing` 0.5, `streamline` 0.5, `simulatePressure` true, `easing` t => t, `start`/`end` `{cap: true, taper: 0 | number | true, easing}` (cap is ignored when taper > 0), `last` (true means the stroke is complete). Negative `thinning` makes pressure thin the line. `getStroke` returns an outline polygon. Render it via `getSvgPathFromStroke` → `<path d>`, or `new Path2D(d)` + `ctx.fill()`. Outlines may self-intersect; the README suggests `polygon-clipping` for a flat path. There are ports in Dart, Odin, Python and Rust. — [perfect-freehand README](https://github.com/steveruizok/perfect-freehand)
- Internals: streamline interpolates each point toward the previous by `t = MIN_STREAMLINE_T + (1 - streamline) * STREAMLINE_T_RANGE`, except the final point when `last` is true. Round caps use 13 start and 29 end segments. `FIXED_PI = PI + 0.0001` works around "browser rendering artifacts". — [perfect-freehand getStrokePoints.ts](https://github.com/steveruizok/perfect-freehand/blob/main/packages/perfect-freehand/src/getStrokePoints.ts); [constants.ts](https://github.com/steveruizok/perfect-freehand/blob/main/packages/perfect-freehand/src/constants.ts)
- **tldraw** vendors the algorithm in `packages/tldraw/src/lib/shapes/shared/freehand/` (getStroke, getStrokePoints, getStrokeOutlinePoints, svg). — [tldraw freehand folder](https://github.com/tldraw/tldraw/tree/main/packages/tldraw/src/lib/shapes/shared/freehand). Its settings in `getFreehandOptions`:
  - real pen: `size: 1 + strokeWidth * 1.2, thinning: 0.62, streamline: 0.62, smoothing: 0.62, simulatePressure: false, easing: t*0.65 + sin(t*PI/2)*0.35`
  - finger/mouse: `size: strokeWidth, thinning: 0.5, streamline: modulate(strokeWidth,[9,16],[0.64,0.74]), smoothing: 0.62, simulatePressure: true, easing: easeOutSine`
  - solid (non-"draw" dash): `thinning: 0`
  - `last` is set when the shape is complete.

  — [tldraw draw/getPath.ts](https://github.com/tldraw/tldraw/blob/main/packages/tldraw/src/lib/shapes/draw/getPath.ts)
- **Excalidraw** variable-width freedraw calls perfect-freehand `getStroke` with `size: strokeWidth * 4.25, thinning: 0.6, smoothing: 0.5, streamline: element.strokeOptions?.streamline ?? default, easing: easeOutSine, last: true` and `simulatePressure` from the element. The source comments call these "magic numbers backed by visual verification". A newer constant-width mode builds the outline with the `LaserPointer` engine (`size: strokeWidth * 1.4`, pressure pinned to 1). When a pen is first detected, Excalidraw switches the default stroke variability to "variable". — [Excalidraw packages/element/src/shape.ts](https://github.com/excalidraw/excalidraw/blob/master/packages/element/src/shape.ts); [Excalidraw App.tsx](https://github.com/excalidraw/excalidraw/blob/master/packages/excalidraw/components/App.tsx)
- tldraw stores pressure rounded to 2 decimals and only for real pens. Non-pressure strokes omit z (2D points). — [tldraw Drawing.ts](https://github.com/tldraw/tldraw/blob/main/packages/tldraw/src/lib/shapes/draw/toolStates/Drawing.ts)
- tldraw's "Dynamic Size" preference, added June 2024, scales new shapes inversely with zoom via the shape's `scale` prop. — [tldraw draw-shape docs](https://tldraw.dev/sdk-features/draw-shape); [tldraw release notes 2024-06-20](https://tldraw.dev/blog/release-notes/release-notes-20240620)

**What the project does today**
- Every stroke renders as a raw polyline with `lineCap = lineJoin = 'round'` (canvas) and `stroke-linecap/linejoin="round"` (SVG). Single-point strokes are a circle of radius `max(1, size/2)`. There is no smoothing, streamlining or pressure. Brush sizes are `[1, 2, 4, 6, 8, 10, 12, 14, 18, 24, 32, 38, 45, 54, 64]`. — [repo: stroke-json/canvas.ts](apps/web/src/lib/features/stroke-json/canvas.ts); [repo: stroke-json/svg.ts](apps/web/src/lib/features/stroke-json/svg.ts); [repo: studio-drawing/state/drawing.svelte.ts](apps/web/src/lib/features/studio-drawing/state/drawing.svelte.ts)

### Inferences
- **Recommended approach for this product.** Keep two brush engines behind a `brush` field in each stroke:
  1. **`round` (current).** A constant-width polyline. Add light input-side streamlining before storing points: perfect-freehand's `getStrokePoints` with streamline ~0.3–0.5, or a 1€ filter. This needs no renderer change and keeps today's exact server parity.
  2. **`ink` (new).** A perfect-freehand outline. Use real pressure when `pointerType === 'pen'`, and simulated pressure for fingers and mice, ideally velocity-in-time based (see section 1). Start from tldraw's pen and finger parameter sets above, with `last: false` while drawing and `true` on commit.
- Pin perfect-freehand to an exact version, or vendor its roughly 300 lines of MIT code with attribution, inside a shared `stroke-json` module that runs in both the browser and the Worker. Store a brush/engine version in the document so retuning parameters never changes already-published art.
- Predicted points: feed `getPredictedEvents()` only into the wet-layer render (with `last: false`), never into stored points.
- Integer document coordinates are the main smoothness limit. A 1-px brush on 768² shows stair-stepping, and if zoom is added, one document unit spans several screen pixels. Store sub-pixel coordinates, e.g. fixed-point ×4 or ×8 integers, or one decimal.
- FigJam/Figma: I found no public engineering source describing FigJam's pen smoothing or pressure (see Gaps).

### Gaps
- No primary source found on FigJam's marker/pen stroke algorithm or prediction. I don't have it, so no claims are made.
- No 2025–2026 comparative quality study of perfect-freehand vs alternatives (lazy-brush, 1€ filter, Catmull-Rom/Chaikin smoothing, Excalidraw's `@excalidraw/laser-pointer`). The comparison would need hands-on prototyping.
- Not verified: whether perfect-freehand's single maintainer intends further feature work. Recent activity is tooling and README only.

## 5. Determinism: can the same stroke geometry render visually identically in browser Canvas2D and in resvg on the server? Pitfalls: antialiasing, eraser (destination-out vs SVG masks), colour spaces, device pixel ratio

### Takeaway
Yes, *visually* identical, if both sides consume exactly the same geometry primitive. That means either a stroked polyline with round caps/joins (today's approach, which already has parity) or a pre-computed filled outline path (perfect-freehand) serialized once with fixed precision and fed to `Path2D(d)` on the client and `<path d>` in the SVG. Pixel-identical output is not achievable or necessary: Chrome (Skia, mostly GPU), Safari (CoreGraphics) and resvg (tiny-skia CPU, a Skia port) anti-alias edges slightly differently. The main real risks are scale/DPR handling, sub-1-px widths, eraser semantics, and library version drift.

### Cited Findings
- The server renders `drawingDocumentToSvg` (`<rect>` background, `<polyline … stroke-linecap="round" stroke-linejoin="round">` per stroke, `<circle>` for single points) with `@resvg/resvg-wasm` using `fitTo: { mode: 'width', value: target.width }`, then `resizeImage` to the target. — [repo: stroke-json/svg.ts](apps/web/src/lib/features/stroke-json/svg.ts); [repo: apps/web/src/lib/server/media/codecs/index.ts `renderSvgToRaster`](apps/web/src/lib/server/media/codecs/index.ts)
- The client canvas renderer uses the same primitives: `lineTo` polyline, round cap/join, `arc` with radius `max(1, size/2)` for single points. — [repo: stroke-json/canvas.ts](apps/web/src/lib/features/stroke-json/canvas.ts)
- tiny-skia (resvg's rasterizer, linebender org): "Unless there is a bug, `tiny-skia` must produce exactly the same results as Skia". It notes that it "doesn't support high-quality antialiasing (hairline stroking in particular)", has no global alpha, uses "just a simple alpha mask" for clipping, and is 20–100% slower than Skia on x86-64 and 100–300% slower on ARM. — [tiny-skia README](https://github.com/linebender/tiny-skia)
- resvg paints on the CPU with tiny-skia, while Chromium paints with Skia via cc::PaintRecord. — [Grida: SVG Rendering, Chromium vs Servo vs resvg](https://canary.grida.co/docs/wg/research/chromium/svg/comparison)
- Skia historically used a special "hairline" mode for line widths < 1, which caused flicker between solid and faint thin lines (2013, may be outdated). — [WHATWG thread on antialiasing of line widths < 1](https://lists.whatwg.org/pipermail/whatwg-whatwg.org/2013-August/082730.html)
- perfect-freehand outline rendering: the same `getSvgPathFromStroke` string can go into an SVG `<path d>` or `new Path2D(d)` + `ctx.fill()`. — [perfect-freehand README](https://github.com/steveruizok/perfect-freehand). `Path2D` has been supported since Chrome 36 and Safari 8 — [MDN BCD api/Path2D.json](https://github.com/mdn/browser-compat-data/blob/main/api/Path2D.json)
- Canvas 2D `colorSpace` option: Chrome 92, Safari 15.2 (default `srgb`). — [MDN BCD api/HTMLCanvasElement.json](https://github.com/mdn/browser-compat-data/blob/main/api/HTMLCanvasElement.json)
- Safari 18.2 fixed a canvas bug where `globalAlpha` was ignored for some `globalCompositeOperation` values. Compositing modes have had engine-specific bugs. — [WebKit Features in Safari 18.2](https://webkit.org/blog/16301/webkit-features-in-safari-18-2/)
- Safari 26.5 added `color-interpolation` for SVG gradients. This is a reminder that SVG colour-interpolation semantics differ across engines when gradients or filters are used. — [WebKit Features for Safari 26.5 (via web-standards.dev)](https://web-standards.dev/news/2026/05/safari-26-5/)

### Inferences
- **Keep a single geometry source of truth in a shared TypeScript module** used by browser, Worker and tests:
  - `round` strokes become `polyline` (SVG) and `lineTo` (canvas), as today.
  - `ink` strokes become `outline = getStroke(points, opts)` and then `d = toPath(outline, precision=2)`. Render `d` as `<path fill=color>` in SVG and `ctx.fill(new Path2D(d))` on the canvas.
  - Both sides use the default nonzero fill rule, so self-intersections render the same.
  - Never let the client use a different renderer for live preview than for the committed stroke, or "pop" artefacts appear on commit.
- Computing the outline in V8 (Workers) vs JavaScriptCore (Safari) can differ in the last ulp of `Math.sin`/`cos`/`atan2`. Rounding coordinates to 2 decimals in `toPath` hides that. Golden-image tests in CI (render a fixture document on the server and compare against a stored PNG with a per-pixel tolerance) will catch library or parameter drift.
- **Antialiasing:** expect at most ±1–2 levels on edge pixels between Chrome, Safari and resvg. That is invisible at 768² for strokes ≥ 2 px. The 1-px brush preset is the most renderer-sensitive case, and with DPR scaling the client draws it at ~2–3 device px while the server draws 1 px at 768. Consider making the minimum brush 2 px, or documenting that 1-px lines look lighter in the published PNG.
- **DPR and scale:** scale the client by `ctx.setTransform` (backing px / 768), never by changing document coordinates. The server should rasterize at the final output size directly (`fitTo`). Its current path (resvg at the target width, then `resizeImage`) adds a second resampling, which softens thin lines relative to the client.
- **Eraser:** the simplest deterministic eraser is a stroke painted in `document.background` colour, which renders identically everywhere. A true alpha eraser needs `destination-out` on the canvas and an SVG `<mask>` or group compositing on the server. That is feasible in resvg, but costlier, and it breaks the per-stroke incremental cache model unless erasers are scoped per layer. With a solid-colour background (the current schema), background-colour erasing is recommended. If forks ever layer a raster base image, revisit it.
- **Colour:** all palette colours are opaque `#rrggbb` sRGB. Canvas defaults to `srgb`, and resvg outputs untagged sRGB that browsers treat as sRGB. Wide-gamut (P3) displays colour-manage both the same way, so no special handling is needed as long as no canvas is created with `colorSpace: 'display-p3'` and alpha blending stays out of the strokes.
- **Data model implications** (needed for pressure and the requested timelapse): add per-point pressure (quantized, e.g. 0–100 or 2 decimals like tldraw), only for pen strokes. Add a per-point time delta in ms, small integers, which enables a faithful timelapse replay and velocity-based pressure. Keep a `brush`/engine version. This grows the document by roughly 30–80% for pen strokes. Given the known large-Bind/`CONNECTION_CLOSED` sensitivity of the Supavisor path (project memory), prefer delta + varint/base64 packing of points in the stored form.

### Gaps
- No published pixel-diff study of resvg vs Chrome Canvas2D vs Safari Canvas2D for stroked polylines or filled outlines. The tolerance figures above are an inference and should be confirmed with a fixture-based diff in this repo's test suite.
- Not verified: whether resvg-wasm's output for round joins on very short, dense integer polylines (many sub-pixel segments) differs visibly from Skia GPU raster.

## 6. UX patterns for drawing details on small phone screens: zoom/pan, brush size relative to zoom, undo gestures, examples from leading apps

### Takeaway
Leading apps converge on four patterns:
- Pinch to zoom and pan with two fingers, with a quick-pinch to fit the canvas.
- Two-finger tap to undo and three-finger tap to redo (Procreate convention), plus visible undo/redo buttons for discoverability.
- A brush size defined in canvas units, so zooming in gives finer detail, with the cursor/preview ring scaled by zoom. tldraw offers an optional "dynamic size" mode that keeps on-screen size constant.
- A pen-mode toggle so fingers navigate while the stylus draws.

For a 768² canvas on a ~390-CSS-px-wide phone, each CSS px is about 2 document units, so zoom is essential for detail. Zoom also requires sub-pixel point storage.

### Cited Findings
- Procreate: two-finger tap = undo, holding two fingers = rapid undo (delay adjustable), up to 250 undo steps. Three-finger tap = redo. Quick-pinch = fit to screen, and its reverse returns to the previous view. Procreate Dreams lets users switch off two-finger-tap undo. — [Procreate Handbook: Gestures](https://help.procreate.com/procreate/handbook/interface-gestures/gestures); [Procreate Dreams Handbook: Prefs](https://help.procreate.com/dreams/handbook/movie-settings/prefs)
- tldraw "Dynamic Size": shapes drawn while zoomed scale inversely with zoom so they look the same on screen. The setting is under Menu > Preferences > Dynamic Size. — [tldraw release notes 2024-06-20](https://tldraw.dev/blog/release-notes/release-notes-20240620); [tldraw draw-shape docs](https://tldraw.dev/sdk-features/draw-shape)
- tldraw keeps finger UI working in pen mode (toolbar taps) and shows an on-canvas "Exit pen mode" button. — [tldraw Pen mode docs](https://github.com/tldraw/tldraw/blob/main/apps/docs/content/sdk-features/pen-mode.mdx)
- Excalidraw: two-finger pinch zoom/pan from pointer events. In pen mode while free-drawing, pinch only pans (scale forced to 1). Safari `gesturestart` is suppressed. A pen-mode toggle button appears in the toolbar and mobile menu. — [Excalidraw App.tsx](https://github.com/excalidraw/excalidraw/blob/master/packages/excalidraw/components/App.tsx); [Excalidraw PenModeButton.tsx](https://github.com/excalidraw/excalidraw/blob/master/packages/excalidraw/components/PenModeButton.tsx)
- The project today has fixed-size display (CSS `h-full w-full`), no zoom/pan and no undo. Brush presets are in document units (1–64), with a semi-transparent brush-preview circle at the pointer. — [repo: DrawingCanvas.svelte](apps/web/src/lib/features/studio-drawing/components/DrawingCanvas.svelte); [repo: state/drawing.svelte.ts](apps/web/src/lib/features/studio-drawing/state/drawing.svelte.ts)

### Inferences
- **Zoom/pan implementation:**
  - Keep a view transform `{scale, tx, ty}`. During a pinch, apply it as a CSS `transform` on the canvas wrapper. That is compositor-only and stays smooth at 60/120 Hz.
  - When the gesture ends, re-render the backing store at the new effective resolution, capped. Convert pointer coordinates to document space with the inverse transform.
  - Clamp zoom (e.g. 1×–8×) and keep the canvas edges reachable.
  - Add "fit" on quick-pinch or double-tap with two fingers. The latter is a less discoverable alternative.
- **Brush size:** keep it in document units (Procreate-like), since the artwork is a fixed 768² image and published size consistency matters. Scale the preview ring by zoom so users see the real footprint. A "dynamic size" option like tldraw's is optional and probably confusing in a party game.
- **Undo:**
  - Two-finger tap = undo and three-finger tap = redo, active in both pen mode and finger mode. In finger mode they come out of the "second finger cancels the stroke" logic, and the cancelled micro-stroke must not land in history.
  - Always show undo/redo buttons, because gestures are undiscoverable on the web.
  - Undo over a stroke list is trivial: pop the last stroke from `tail`. It also fits the timelapse (replay is just the ordered strokes with time deltas).
- **Small phones:**
  - Default to a mid brush size and offer fewer, larger presets.
  - Put tools in a bottom sheet within thumb reach, with the drawable area inset from the screen edges (it avoids the iOS and Android back-gesture zones).
  - Show the brush preview only for hover-capable pens or mice, not under a finger. The current overlay draws a circle under the finger on every move.
  - Consider a "detail mode" that temporarily zooms to 2–3× around a double-tapped region.

### Gaps
- No authoritative, recent (2025–2026) UX study specific to phone-sized web drawing games. The patterns above come from Procreate, tldraw and Excalidraw documentation and code, not from usability research.
- I did not find documentation of how Skribbl.io / Gartic Phone-style web party games handle zoom on phones. They appear not to offer it, but that is unverified.
